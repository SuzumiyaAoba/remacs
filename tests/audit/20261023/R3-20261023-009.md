二つのファイル監視の通知が待機しているとき、先に処理した `file-notify` コールバックが Lisp の error を通知すると、Remacs は後続の別ファイルの通知も失います。呼び出し元で error を捕捉して `read-event` を再実行しても届きません。GNU Emacs 31.1 は次の通知を処理できます。

## 再現手順

macOS/kqueue 環境で以下を `notify-errors.el` として実行します。途中の短いループはイベントポンプを呼ばず、二つの変更が待機する状態を作ります。

```elisp
;;; -*- lexical-binding: t; -*-
(require 'filenotify)
(let ((first (make-temp-file "notify-first-"))
      (second (make-temp-file "notify-second-"))
      watch1 watch2 seen (errors 0))
  (unwind-protect
      (progn
        (setq watch1
              (file-notify-add-watch
               first '(change)
               (lambda (event)
                 (when (eq (nth 1 event) 'changed)
                   (push 'first seen)
                   (error "audit notification callback")))))
        (setq watch2
              (file-notify-add-watch
               second '(change)
               (lambda (event)
                 (when (eq (nth 1 event) 'changed) (push 'second seen)))))
        (write-region "first" nil first nil 'silent)
        (let ((end (+ (float-time) 0.1)))
          (while (< (float-time) end)))
        (write-region "second" nil second nil 'silent)
        (let ((end (+ (float-time) 0.1)))
          (while (< (float-time) end)))
        (let ((tries 0))
          (while (and (not (memq 'second seen)) (< tries 100))
            (condition-case nil (read-event nil nil 0.02)
              (error (setq errors (1+ errors))))
            (setq tries (1+ tries))))
        (prin1 (list (and (memq 'first seen) t)
                     (and (memq 'second seen) t)
                     (> errors 0)))
        (terpri))
    (when watch1 (ignore-errors (file-notify-rm-watch watch1)))
    (when watch2 (ignore-errors (file-notify-rm-watch watch2)))
    (delete-file first)
    (delete-file second)))
```

```sh
./target/debug/remacs -Q --batch -l notify-errors.el
/path/to/emacs-31.1 -Q --batch -l notify-errors.el
```

期待結果（GNU）: `(t t t)`。一つ目の通知・二つ目の通知・捕捉したエラーがすべて存在します。
実際（Remacs）: `(t nil t)`。一つ目のエラー後、約2秒待っても二つ目の通知が届きません。

コールバック内の error だけを除去した対照は、両方 `(t t nil)` で通知を二つとも処理します。

## 原因候補

`src/lisp/builtins/filenotify.rs:657` 付近の `drain` は `std::mem::take` で `PENDING` 全体をローカルの `raw` へ取り出し、`dispatch_kevent(i, fd, fflags)?` で順次処理します。途中で Lisp コールバックがエラーを返すと、まだ処理していない `raw` の残りも drop されます。エラー伝播前に未処理通知を維持する必要があります。

確認時 HEAD: `ddb739830ec89144612d2cf7755b1115ef5b1058`。実行バイナリのランタイムは `aeaff55` と同一で、両HEAD間の filenotify 実装に変更なし。macOS/aarch64、GNU Emacs 31.1。証拠: `tests/audit_filenotify_lifecycle.el` の `notify:callback-error-queue` と成功対照、`tests/audit/20261023/filenotify-error-queue-results.json`。

既存の file-notify 関連 Issue を照合。#346 の配列アクセス panic、#348 の reader thread 再生成漏れとは、再現条件・修正箇所が異なります。
