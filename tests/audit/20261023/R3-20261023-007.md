SQLite の TEXT 結果を Lisp 文字列へ変換するとき、不正な UTF-8 バイトが U+FFFD に置き換わり元データを復元できません。GNU Emacs 31.1 は同じ TEXT の不正バイトを raw-eight-bit 文字として保持します。ASCII・空文字列の TEXT についても GNU は multibyte を返すのに Remacs は unibyte になります。

## 再現手順

```elisp
;;; -*- lexical-binding: t; -*-
(let ((db (sqlite-open)))
  (unwind-protect
      (dolist (sql '("select cast(x'80ff' as text)"
                     "select cast(x'e282' as text)"
                     "select 'a'"
                     "select cast(x'c3a9e38182' as text)"))
        (let ((s (caar (sqlite-select db sql))))
          (prin1 (list (multibyte-string-p s)
                       (string-bytes s)
                       (string-to-list s)))
          (terpri)))
    (sqlite-close db)))
```

```sh
./target/debug/remacs -Q --batch -l sqlite-text.el
/path/to/emacs-31.1 -Q --batch -l sqlite-text.el
```

| TEXT の内容 | GNU Emacs 31.1 | Remacs |
|---|---|---|
| 80 FF | `(t 4 (4194176 4194303))` | `(t 6 (65533 65533))` |
| E2 82（途中で切れたUTF-8） | `(t 4 (4194274 4194178))` | `(t 3 (65533))` |
| ASCII a | `(t 1 (97))` | `(nil 1 (97))` |
| 正常な UTF-8 の éあ（対照） | `(t 5 (233 12354))` | `(t 5 (233 12354))` |

空 TEXT、NUL を含む TEXT、不正な先頭・継続バイト・surrogate・Unicode 範囲外の符号化も比較し、計10ケース中9ケースで差を確認しました。

## 原因候補

`src/lisp/builtins/sqlite.rs:401` 付近の `sval_to_value` の TEXT 分岐が `Value::string(String::from_utf8_lossy(t).into_owned())` を使っています。これにより不正バイトは置換され、ASCII-only の結果には明示的な multibyte 状態も付与されません。GNU の lossless な Emacs 文字列復号と TEXT の表現を保つ処理が必要です。

確認時 HEAD: `aeaff5597e60834c21d464b7ad2a4caf167726dc`、macOS/aarch64、GNU Emacs 31.1。対象実装は未変更。再現群・生出力: `tests/audit_sqlite_text.el` / `tests/audit/20261023/sqlite-text/evidence.json`。

既存 SQLite Issue と `sqlite TEXT` の本文検索を照合。#162 は BLOB の読み出しであり、現行実装の BLOB 分岐は任意バイトを保持するよう修正済みです。本件は別の TEXT 分岐に残るデータ破壊・文字列表現の問題です。
