端末からの ASCII 制御バイト 0x1c〜0x1f が 0x14〜0x17 に変換されます。特に C-_ (0x1f、Undo) が C-w (0x17、kill-region) になり、markがなければ「The mark is not set now」となってUndoされません。

## 実端末での再現

1. 空のファイルを `-Q -nw` で開く。
2. `abc` を入力し、C-a、C-e を押す。
3. `X` を入力し、C-_ を押す。
4. C-x C-s で保存する。

GNUは `abc\n`、Remacsは `abcX\n`。Remacsの端末ログには `user-error: The mark is not set now, so there is no region` が残りました。両側とも描画と正常終了を確認した独立PTYでの結果です。

## 変換そのものの対照

M-: で次の設定を評価してから、PTYへ生バイト `1c 1d 1e 1f` を送信しました。

```elisp
(dolist (code '(20 21 22 23 28 29 30 31))
  (global-set-key (vector code)
    (eval (list 'lambda nil '(interactive)
                (list 'insert (format "<%d>" code))))))
```

GNUの挿入結果は `<28><29><30><31>`、Remacsは `<20><21><22><23>` です。

原因候補: crossterm 0.29.0 のUnixパーサは0x1c〜0x1fを CONTROL + '4'〜'7' として返します。src/term/mod.rs の key_event_to_code がこれをASCII文字の `& 0x1f` で変換するため、20〜23になっています。crosstermの制御文字表現を元のコードへ戻す処理が必要です。既存#297の修飾付きHome等の名前変換とは別の経路です。

対象: `926cbfc7fe1ddde28c53d0555be1f6b99563535b` + 調査時の既存 shell/display 作業ツリー変更、macOS/aarch64、GNU Emacs 31.1。固定バイナリ SHA-256: `37aec7800115143d785086fa184114757237776c93c892e30696644b5c255017`。実PTYへのアクセスが必要なため、/dev/tty制限のない環境で比較しました。
